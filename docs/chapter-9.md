# 第9章 アジャイル開発

この章は、Entity、Value Object、Service、Factory、Repositoryというオブジェクトの語彙から、ドメイン駆動設計（DDD）とアジャイル開発へ議論を広げる。個々の技術を別々の作法として扱うのではなく、変化に応じて再計画しながら人と対話するための手段としてつなげている。

DDD、テスト駆動開発、依存性注入、クリーンアーキテクチャは、いずれもソフトウェアを変更しやすくし、顧客との対話を支えるための道具である。技術的な手段の先に、倫理的に仕事をするという目的を置くことがこの章の結論になる。

## 章の主張

オブジェクトの語彙（Entity / Value Object / Service / Factory / Repository）は、ユーザーと開発者が共通言語で対話するための分類である。DDD・アジャイル・クリーンアーキテクチャは、すべて「変化に応じて再計画しながら人と対話する」という一つの目的に収束する。

ソフトウェア開発の技術的な手段は、倫理的に仕事をするための手段である。

## 前提

- ビジネスロジックとユーザーの問題領域を理解できる「実践的モデラー」が存在すること
- 顧客との直接対話が制度的に許可されていること
- チームにユニットテストを書く意思があること
- ドメインが十分な複雑さを持つこと（シンプルなCRUDや短命なシステムには適用対象外）

## 実務上の効きどころ

- **Repositoryのインターフェースをビジネスロジック側から先に決める**：SQLに近い汎用インターフェースを避けることでモックが単純になり、テストが安定する。テストを書いている現場なら今日から導入できる
- **Value Objectをイミュータブルに寄せる**：インスタンス管理の仕組みが不要になる。既存コードの局所リファクタリングから始められる
- **仕様書より先に1〜2日のモデルコードを書く**：仕様の議論をコードで始めることで、認識のズレを早期に発見できる。ただし、経験者が書くことが前提になる

## 弱点と例外

- **実践的モデラーがいない現場**では、DDDのモデル駆動設計の初期フェーズを担う人材が存在しない。代替手段は本文に示されていない
- **多重下請け構造**では、契約・発注フローが固まる前に「ヒアリング前のモデルコード」を書く工数の名目が立たない
- **「ウォーターフォールは存在しなかった」**という歴史的断定は著者解釈の域を出ており、「方法論として命名されていなかった」と「存在しなかった」を同一視している点で反論可能
- **「本物のアジャイルはアーキテクチャで見分けられる」**は単方向の推論である。アーキテクチャが健全でもプロセスが機能不全なケース、またはその逆を説明できない
- **「2020年以降はパラダイムが落ち着いている」**という見通しは、LLM・AI開発の台頭によってすでに反証されている

## 議論用の問い

1. **DDDを「正攻法」と呼ぶ強さは妥当か**：Evans自身が「DDDは複雑なドメインにのみ適用すべき」と述べているとすれば、「アジャイルへの正攻法」という断定はどこまで成立するか
2. **実践的モデラーがいない現場でどうするか**：本文はモデラーの重要性を述べるが不在時の代替を示さない。現場ではこの人材をどう育てるか、あるいは外部に求めるかの判断基準をどう持つか
3. **「ビジネスロジック側からインターフェースを決める」原則を、既存の大規模レガシーコードに後付けで適用するとき何が最初の障壁になるか**

== 理解の視点

**拾った主張**

- オブジェクトは役目で呼び分けられる。**Entity**（実世界に対応する・インスタンスの一意性が必須）、**Value Object**（一意性不要・イミュータブル・参照透過）、**Service**（DIで組み立てる静的モジュール・参照透過）、**Factory**（オブジェクトを生成するオブジェクト）、**Repository**（エンティティの一意性を担保する特殊なファクトリサービス）の5種
- Active Recordはエンティティ・リポジトリとは別物。サードパーティへの強依存とインスタンス一意性の非保証が理由
- 同じ用語でも「何を中心とするコンテキストか」によって指す実体が異なる。DDDはこれを**境界づけられたコンテキスト**と呼ぶ
- **DDD**はプロセスの手法。先にコードでドメインモデルを書き（モデル駆動設計）、**ユビキタス言語**（ユーザーと開発者の共通語彙）を確立し、**要求の洗練**を反復することが中心的活動
- DDDはドメインモデルの設計そのものは含まない。設計の質は**実践的モデラー**の力量に依存する
- アジャイル宣言の4つの価値観は、個人と対話、動くソフトウェア、顧客との協調、変化への対応である
- アジャイルとは進捗報告ではなく**再計画**の反復である。TDD・DI・クリーンアーキテクチャはすべてこの目的につながっている
- **ウォーターフォール**という名の開発手法は歴史上に実在したわけではなく、ロイスの図が誤解されて象徴的な架空の悪者として広まった言葉である
- 日本のSIer多重下請け構造は制度的に生まれたもので、ウォーターフォール的な体質を好む動機が経済的・制度的に生じた
- **偽物のアジャイル**かどうかはアーキテクチャの安定度分布を軽視しているかどうかで見分けられる
- クリーンアーキテクチャは2017年発刊だが内容は15年前のオブジェクト指向であり、本質的に新しいことはない

**気にした論点**

- **モデル駆動設計（MDD）**と、「コードを機械的に生成する逆方向の手法（同名の別物）」が注記で区別されているが、混同しやすい
- リポジトリは「汎用的に作るのではなく、ビジネスロジック側から使い方を決めてから作る」とあるが、何が具体的に変わるのかイメージしにくい
- Active Recordが「一意性を担保しない」と言われる理由が、技術的にまだ腑に落ちていない
- ウォーターフォール史の流れ（ロイスの図 → 米国防省の誤解 → ドキュメント偏重 → 日本SI制度）が長くて因果関係を追い直した

**結論**

この章は、オブジェクトの語彙分類・DDD・アジャイル宣言の三つを一本の線でつなぎ、「ソフトウェア開発技術はすべて人との対話と倫理的な仕事をするための手段である」と言い切る話である。

**残した保留**

- Active Recordがエンティティ・リポジトリと「分けて考えないといけない」技術的な理由がまだ曖昧
- 「境界づけられたコンテキスト」は定義だけ出てきたが、実際の設計でどう使うのかは示されていない
- コラムの1995〜2020年史を読んだが、現時点で「何が解決済みで何がまだ問題として残っているのか」が整理できていない

== 実務の視点

**拾った主張**

- **Repositoryはビジネスロジック側からインターフェースを決める**（適用条件：ビジネスロジックの単体テストを書く意思があること）。先に汎用的に作るとSQLに近いインターフェースになり、モックが複雑になってテストが壊れる
- **Value Objectはイミュータブルに寄せる**（適用条件：状態管理が不要なデータ）。インスタンス管理の仕組みが不要になり、コードがシンプルになる
- **Entityのインスタンス一意性を担保しないO/Rマッパー（Active Record系）は、エンティティ用語と分けて考える**。混同したまま設計するとインスタンス重複バグが潜む
- **DDDの最初のモデルコードは「1〜2日の仮説」として書く**（適用条件：具象も想像できる経験者が書くこと）。分厚い仕様書より先に動くモデルコードで議論を始める
- **アーキテクチャが汚いと変更リスクを説明できなくなり、顧客との対話が成立しなくなる**。「どこが壊れるかわからない」では理由を堂々と言えない

**気にした論点**

使える場面：

- Repositoryのインターフェースファーストは、テストを書いている現場なら即導入可能。コストは低い
- Value Objectのイミュータブル化は、既存コードの局所的なリファクタリングから始められる

使えない場面・導入コスト：

- DDDのモデル駆動設計は「実践的モデラー」が必須。その人材が現場にいない場合の代替手段は本文に書かれていない
- 「ヒアリング前にモデルコードを書く」工程は、契約・発注フローが固まった多重下請け構造では工数の名目が立たない。誰がその費用を持つかが不明なまま
- ユビキタス言語の確立は、顧客との直接対話が許可されていない現場では成立しない

既存手法との差分：

- 「先に仕様書を固めてからコードを書く」プロセスとは根本的に順序が逆。ウォーターフォールの歴史説明は長いが、要は「仕様書ではなくコードで検証する」という一点に集約される

**結論**

Repositoryのインターフェースをビジネスロジック側から先に決める設計手順は、テストのしやすさと抽象化の質に直接効くので、今の現場で今日から使える。

**残した保留**

- **実践的モデラーが社内にいない場合**、誰がモデル駆動設計のイニシャル工程を担うのか。外注できるスキルではないと本文は言っているが、その場合の現場立ち上げ方法は不明
- **DDDの「まずモデルコードを書く」フェーズ**を契約前・見積もり前に実施することへの現実的な合意形成手順が書かれていない。費用化・正当化の方法が現場ごとに異なる
- **ユビキタス言語の境界**（bounded context）は概念として理解できるが、実際の現場で「どこで区切るか」を誰がどう判断するかの基準が本文では示されていない

== 批評の視点

**拾った主張（批評付き）**

- **「問題について知っているのはユーザーだが、どのように解決するのが正しいのかを知っているのは開発者だ」**（p.318）
  → 開発者がドメインを十分に理解していない場合、あるいはユーザー側がソフトウェア経験を持つ場合、この非対称は逆転する。「知っているのは開発者」という断定は前提条件が多い
- **「ドメインモデルは1日か2日で書ける」**（p.319）
  → 「なんら実機能がない抽象」という限定はあるが、ドメインの複雑さやチーム規模によって大きく変わる。根拠となる条件が示されていない
- **「DDDはアジャイルソフトウェア開発への正攻法だ」**（p.322）
  → 「正攻法」は強い断定。DDDが有効なのは複雑なドメインを持つシステムに限るという前提が明示されていない。シンプルなCRUDや短命なシステムには過剰になりうる
- **「開発の進捗を確約する方法は本質的にない」**（p.325）
  → 「本質的に」という修飾が強すぎる。ベロシティ計測や十分に細分化されたタスク管理など、確度の高い見積もり手法は存在する
- **「ウォーターフォール開発という方法論は歴史上存在しなかった」**（p.329）
  → 「方法論として命名されていなかった」と「存在しなかった」は意味が異なる。単方向プロセスが多くの組織で実際に実施されてきた事実は否定できず、「存在しなかった」は過剰な言い方になりうる
- **「本物のアジャイルかどうかはアーキテクチャで見分けられる」**（p.335）
  → 「アーキテクチャが良い＝本物のアジャイル」は単方向の推論。アーキテクチャが健全でもプロセスが機能不全なケース、逆に粗くても対話と再計画が機能しているケースはどちらも説明できない
- **「今はパラダイムに落ち着きがある。変化が激しすぎてついていけないことはもうない」**（p.339）
  → 本書の記述時点（2020年前後）の楽観的見通しであり、LLM・AI開発の台頭によってソフトウェア開発のパラダイムは再度急変しており、すでに時代によって反証されている状況にある

**気にした論点**

前提の未明示：

- 「開発者が問題解決を知っている」：業務ドメイン理解の深さが前提になっているが、それが確保されているかどうかは組織・案件によって大きく異なる
- DDDの実践が「経験豊かな実践的モデラー」に強く依存しているが、そういった人材がいない場合の議論が章内に存在しない

論理の飛躍：

- 「ウォーターフォールは存在しなかった」は著者の歴史解釈による部分が大きく、「方法論として意図的に選ばれていなかった」と「存在しなかった」を同一視している
- アジャイル宣言の署名者にマーチン・ファウラー・ベックが含まれることを根拠にDDDとアジャイルの接続を示しているが、人物の重複は「正攻法」という強さを保証しない

過剰一般化：

- 「包括的なドキュメントを書きたがる人はプログラムを書けない」（p.324）：傾向としては理解できるが、「書けないので」という動機帰属には反例がある
- 「本物のアジャイル判定基準としてのアーキテクチャ」：実証的な裏付けなしに判定指標として提示されている

**結論**

アジャイル宣言・DDD・クリーンアーキテクチャが同じ問題意識から生まれたという接続は、署名者の名前という具体的な根拠で示されており、この章の主張の中で証拠と論理が最も支えられている部分である。

**残した保留**

- DDDを「正攻法」と呼ぶ主張は、Evans自身が「DDDは複雑なドメインにのみ適用すべき」と述べていることと整合するかの確認が必要
- 「ウォーターフォールは存在しなかった」という歴史的断定は、著者解釈の域を出ておらず、異なる歴史観が提示された場合に主張が崩れる可能性がある
- 「本物のアジャイルはアーキテクチャで見分けられる」という判定基準は、逆方向の推論（アーキテクチャが良い→本物）に循環するリスクがあり、追加検証が必要
- 「2020年以降はパラダイムが落ち着いている」という見通しは、現時点（2026年）でAI・LLMの台頭により再検討を要する状態にある
