# 第8章 デザインパターン（前半）：多態性とオブジェクト生成

前半は、デザインパターンを設計上の概念に名前を付けて共有するための語彙として捉える。Iteratorで反復を抽象化し、Template MethodとBridgeで多態性を組み立て、SingletonとAbstract Factoryでオブジェクト生成の責務を考える。

## 章の主張

デザインパターンとは概念に名前を付けて共有する道具であり、この章の核心は「対象が抽象ならファクトリも抽象でなければならない」というAbstract Factoryの原則にある。Iterator・Template Method・Bridge・Singletonはその伏線として、オブジェクト生成と多態性の表現力を段階的に説明する構造になっている。

## 前提

- チームがGoFの語彙をある程度共有していること（共有がなければパターン名はかえって摩擦を生む）
- DIコンテナが使える環境であること（Singleton否定とAbstract Factory推奨の両方に共通する暗黙の前提）
- バリエーションの軸数が設計段階で見通せること（Template Method vs Bridge の選択判断に必要）
- 単一継承モデルの言語環境（PHPを中心とするコード例が前提とする制約）

## 実務上の効きどころ

- **Iterator**：大容量データのストリーミング処理・異種データソースの統一ループ。`toArray()`への逃げが全件メモリ展開になる場面で判断基準として使える
- **Template Method**：コピーコードの抑制とミス防止が目的のリファクタ局面。クライアントには最小インターフェースを渡す
- **Bridge**：継承ツリーの爆発に気づいた段階での構造改修。独立した軸が複数存在すると判明したとき委譲への切り替えサインとして使う
- **Abstract Factory**：動的生成オブジェクトを扱う場面全般。生成と使用の分離が崩れているコード（具象ファクトリへの直接参照）の発見基準として「PSR-11/PSR-17の構造と比較する」が実践的な指標になる

## 弱点と例外

- **Template Methodの適用条件記述が不安定**：「予測できない場合に安心して使える」という一文は論理的に逆方向に読める。「バリエーションがある程度予測可能な場合に限定して有効」という趣旨であれば表現に飛躍があり、適用判断の基準として機能しない
- **Singleton否定の対象が限定的な可能性**：「本質的にグローバル変数」という強い断定は、`getInstance()`を直接呼び出すスタイルへの否定にとどまる可能性がある。インターフェース経由でDI注入すれば問題の多くは緩和されるため、パターン自体への否定とは区別が必要
- **DIコンテナを前提とした主張の射程**：Singleton代替・Abstract Factory管理の両方がDIコンテナ前提であり、レガシー環境・小規模スクリプト・組み込みへの代替案は本章に存在しない
- **Abstract Factory「最重要」の根拠が実例止まり**：PSR-11/PSR-17がAbstract Factoryを採用している事実は有用な例示だが、他パターンとの比較軸がなく、「最重要」は著者の価値判断として読む必要がある
- **Singleton内部状態の許容境界が曖昧**：「書き換え可能なプロパティを持たせてはいけない」と「技術的に内部変数を隠し持つのは仕方ない」が並存しており、どこからが「ユーザーにとって有意な状態」かが不明確

## 議論用の問い

1. Template MethodとBridgeの選択基準「軸が1つか2つ以上か」は、設計の初期段階で判定できるか。軸の数が後から増えるケースが多い現実において、最初からBridgeを選ぶ方が安全という結論にならないか。

2. Singletonの否定は「`getInstance()`直接呼び出しスタイル」への否定なのか、パターンそのものへの否定なのか。インターフェース経由でDI注入すれば「本質的にグローバル変数」という批判は成立しなくなるのではないか。

3. Abstract Factoryの導入にはインターフェース追加とパッケージ再構成が同時に必要になる。「具象ファクトリで妥協してよいフェーズの終わり」をどこで判断するか。設計の固まり具合をどう見極めるか。

== 理解の視点

**拾った主張**
- **デザインパターン**とは、ソフトウェア設計に関する共通の語彙・習慣のこと。GoF本（1994年）が最初に命名した。
- パターン学習の価値は、コードのコピペではなく「概念と名前を共有する」ことにある。
- **Iteratorパターン**：「要素を列挙する」という行為を、配列・ファイルシステム・ストリームに関わらず同一の抽象概念として扱えるようにしたもの。配列よりも抽象度が高い概念。
- **Template Methodパターン**：アルゴリズムの大枠を抽象クラスに書き、異なる部分だけを派生クラスで穴埋めする。継承の「制約の多さを逆手に取る」ことで生産効率を上げる。抽象の問題をより細かい粒度に分解する（抽象レベルの変換）役割もある。
- **Bridgeパターン**：バリエーションが2軸以上あるとき、is-aの継承ツリーではなく、has-aのインスタンス組み合わせで多態性を実現する。Template Methodで設計できるのは1系統だけ。
- **Singletonパターン**：インスタンスをひとつに限定するパターン。本質的にはグローバル変数であり、状態（書き換え可能なプロパティ）を持たせてはいけない。現代での直接利用は稀。
- シングルトンが必要なケースでは、Singletonパターンのクラスより**DIコンテナによるインスタンス管理**の方が優れている（コンストラクタパラメータを持てる、単体テストが容易）。
- **参照透過性**：同じ引数で呼び出したとき常に同じ結果が返ること。シングルトンや疑似シングルトンはこれを満たさなければならない。
- **Abstract Factoryパターン**：動的なオブジェクト生成を抽象化するパターン。「対象オブジェクトが抽象なら、そのファクトリも抽象でなければならない」。使用側（Buyer）には抽象だけが入り、生成側（Shop）には具象が入る。ファクトリ自体は状態を持たない静的モジュールなのでDIコンテナで管理できる。
- PSR-11（DIコンテナ規約）とPSR-17（HTTPファクトリ規約）は、Abstract Factoryパターンの実例として紹介されている。

**気にした論点**
- **「参照透過性」**という言葉が初出でわかりにくかった。「透明」の意味が「不透明な事情に左右されない」という説明で少し追うのに時間がかかった。
- **「ファクトリ自体は静的モジュール」**という表現。「動的なデータを生成するオブジェクトでも、そのファクトリ自身は状態を持たない」という意味だと理解したが、「動的」と「静的」が混在する説明の流れがもう一歩飲み込みにくかった。
- **BridgeとTemplate Methodの使い分け判断**。「軸が1つか2つ以上か」という基準は理解したが、設計段階でどう見分けるかのイメージがまだぼんやりしている。

**結論**
デザインパターンとは「概念に名前を付けて共有する」ことであり、この前半ではIterator（反復の抽象化）・Template Method/Bridge（多態性の設計）・Singleton/Abstract Factory（オブジェクト生成の抽象化）の3テーマを通じて、オブジェクト指向の表現力をどう設計に活かすかを説明している章。

**残した保留**
- **参照透過性の感覚**：定義は分かったが、「状態を持たせてはいけない」という禁止事項が設計上どのくらい強い制約なのかがまだ肌感覚として掴めていない。
- **PSR-11/PSR-17の例**：「Symfony ServiceContainerがAbstract Factoryを実装している」という話は、実際にコードを触ったことがないため、説明を読んでわかった気になっているだけかもしれない。
- **Abstract FactoryとBuilderの違い**：ファイル2の末尾にBuilderパターンへの言及があったが、「複雑なオブジェクト構造を作る」という説明だけでは、Abstract Factoryとの住み分けがまだぼんやりしている。

== 実務の視点

**拾った主張**
- **Iterator は配列より上位の抽象**（適用条件：大容量ファイル・DBレコードのストリーミング処理、異種データソースを同一ループで扱いたい場面）。`toArray()` に逃げると全件メモリ展開になる。
- **Template Method は「コピーコードを防ぐための制約」として使う**（適用条件：バリエーションが事前に予測でき、実装者のミスを防ぎたい場面）。クライアントには abstract クラスでなく最小インターフェースを渡すこと。
- **Bridge はバリエーションが2次元以上になったとき継承ツリーを捨てて委譲に切り替えるサイン**（適用条件：Material × Shape のように独立した軸が複数存在する場合）。
- **Singleton パターンのクラスは現代では使わない。DI コンテナで代替せよ**（適用条件：コンテナが使える環境限定）。状態を持たせたら即アンチパターン。
- **「対象が抽象ならファクトリも抽象」—Abstract Factory**（適用条件：動的生成オブジェクトを使う場面全般）。PSR-11・PSR-17 が実例として明快。ファクトリ自体は DI コンテナで静的管理する。
- **パターン名は共通語彙として機能する**（適用条件：チームにある程度の OOP リテラシーがある場合）。

**気にした論点**
- Template Method の「コピーコードを大量発生させるよりマシ」という動機は消極的。既存コードのリファクタ局面では有効だが、新規設計で最初から選ぶ判断基準が弱い。「バリエーションが予測できる」の見極めは属人的になりやすい。
- Bridge の導入タイミングが難しい。継承ツリーが爆発する前に気づけるかは経験依存。気づいた時点で継承ツリーを壊す改修コストが発生する。
- Abstract Factory は正しいが、導入時にインターフェース追加とパッケージ再構成が同時に必要になる。小規模アプリや初期フェーズで「まだ具象ファクトリで妥協」と判断したときの戻り方が問題になる。
- Singleton 代替として DI コンテナが前提だが、DI コンテナを使っていない既存プロジェクトへの処方箋が本章にはない。

**結論**
Abstract Factory の「対象が抽象ならファクトリも抽象」を設計判断の口ぐせにする。生成と使用を分離したつもりで具象ファクトリを直接参照している箇所が自分のコードにも残っており、そこから依存スパゲッティが始まる。

**残した保留**
- Template Method と Bridge の判断分岐点：「バリエーション軸がひとつなら Template Method、ふたつ以上なら Bridge」でいいのか、それとも別の指標があるか。
- DI コンテナがない環境（レガシー PHP、組み込み系など）でシングルトンを避けるための代替パターンが未提示のまま。現場で使えるかはコンテナ前提の度合いで変わる。
- Abstract Factory を「まだ設計が固まっていない段階では具象ファクトリで妥協もある」と書いているが、妥協してよいフェーズの終わりをどこで判断するか。

== 批評の視点

**拾った主張**

① GoFパターン学習がコミュニケーション効率を向上させる
→ 崩れる条件：チームや相手がGoF語彙を共有していない場合。語彙が共有されていなければ、逆にパターン名が伝わらず摩擦を生む。

② Iteratorは「配列よりも抽象度の高い概念」
→ 崩れる条件：「抽象度が高い」の基準が明示されていない。FilesystemIteratorやストリーミングの例はIteratorの有用性を示しているが、それが「抽象度の高さ」の証拠なのか「適用範囲の広さ」の証拠なのかが区別されていない。

③ Template Methodパターン適用条件：「予想外のものになる未来があまり予測できない場合なら、安心して継承を選べる」
→ 崩れる条件：「予測できない＝安心」という論理構造が逆に読める。直後に「慎重に考えて選ばないといけない」と書いてあり、この一文は条件説明として不安定。

④ Singletonは「本質的にグローバル変数」
→ 崩れる条件：インターフェースを介してDI可能である点は同節で言及されている。`getInstance()`を直接呼ばず、コンストラクタ注入経由で渡す場合はグローバル変数としての問題が緩和されるのに、「本質的に」という強い断定が維持できるかは疑わしい。

⑤ Singletonの使用機会は「現代では極めてまれ」
→ 崩れる条件：テキストは「DIコンテナが使える場合」を前提に話を進めているが、DIコンテナが使われない設計環境への言及がない。「極めてまれ」はDIコンテナを前提とした文脈に限定される主張である。

⑥ Abstract Factoryは「最重要パターン」。他のパターンは「誰でも考えたら思いつくようなやり方に名前が付いているだけ」
→ 崩れる条件：同章でBridgeやTemplate Methodについて「is-aとhas-aの混同」「継承爆発」という非自明な落とし穴を説明するために使っている。「誰でも思いつく」ならば、それらの陥穽も誰でも気づけることになり、パターン説明の意義が自己矛盾する。

⑦ GoFパターンには「時代を超えた普遍性」がある、一方「現代では読み替えが必要」
→ 同一節内で両方を主張しているが、「どの部分が普遍で、どの部分が陳腐化しているか」の基準が示されていない。

**気にした論点**
- テキスト全体を通じてPHPのコード例が使われているが、「言語を問わず適用できる普遍的な原則」として語られている。言語依存の特性が、原則の一般性にどこまで影響するかの境界が明確でない。
- Abstract FactoryをPSR-11・PSR-17の実例で説明する部分は有効だが、「だからAbstract Factoryが最重要」という帰結は示されていない。PSR規格がAbstract Factoryを採用している事実は、パターンの重要性の例示であって証明ではない。
- 「Singletonは書き込み可能なプロパティを持たせてはいけない」という制約と、「技術的な理由で内部に変数を隠し持つのは仕方ない」が並存しており、許容範囲の境界が曖昧。

**結論**
「対象が抽象ならファクトリも抽象でなければならない」というAbstract Factoryパターンの必然性については、SDPとDIPの組み合わせとPSR規格の実例によって比較的一貫した論理的支持がある。

**残した保留**
- Template Methodパターンの適用条件の文章は、読み取り方次第で意味が逆転する。著者の意図が「派生クラスのバリエーションがある程度予測可能な場合に有効」であるなら、表現の精度が不足しており、反証というより解釈の揺れとして残る。
- Singleton否定の根拠（「本質的にグローバル変数」）は、インターフェース経由でDIした場合にも成立するかが検証されていない。この点を掘り下げると、Singletonそのものへの否定が実装スタイルへの否定にとどまる可能性がある。
- Abstract Factoryを「最重要」と断言する根拠として示されているのは実例のみであり、他パターンとの比較評価の軸が提示されていない。この主張は著者の価値判断として読むべき。
