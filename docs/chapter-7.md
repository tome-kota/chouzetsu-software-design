# 第7章 依存性注入

この章の中核は、クラスの依存を常に外部から与える（コンストラクター注入）ことで、「使用の責務」と「生成の責務」を分離し、単体テストしやすく変更に強い構造を得るという考え方にある。DI コンテナは、その生成管理を一般化したフレームワークであり、手書きファクトリの代替として機能する。

![第7章 依存性注入の要点](/infographics/chapter-7.png)

## 章の主張

クラスの依存をコンストラクター注入で外部から与えると、クラスは依存を生成せずに使用だけを担当できる。生成の責務を Factory や DI コンテナへ分離することで、依存の差し替えと単体テストが容易になり、変更に強い構造が得られる。DI を徹底すると依存は最上位のルートオブジェクトから組み立てられ、DI コンテナによってその管理を設定として一般化できる。

## 前提

- 複数のクラスが連鎖して依存し合う規模のコードベースを対象とすること
- コンストラクター引数として依存を受け渡せる言語・フレームワーク環境が整っていること
- インダイレクション（抽象層やインターフェース）の追加コストを上回るだけの変更耐性・テスト容易性の恩恵が得られる規模と期間のプロジェクトであること
- イミュータブルなオブジェクトはシングルトン的に扱えること。マルチスレッドや識別性が必要なケースは前提外とする

## 実務上の効きどころ

- クラス内で直接 `new` しているコードがあり、依存を差し替える可能性が見えている箇所
- コンストラクターの依存一覧を見ることで、結合度の肥大を早期に検知したい場面
- 複数人で並列開発しており、クラス設計の変更のたびに DI 設定ファイルを編集することで起きるコンフリクトを減らしたい場面
- 個人開発や短期開発ではなく、長期保守を前提としたプロジェクトで、最初のアーキテクチャを選択する場面

## 弱点と例外

- **オートワイヤリングの限界**: 同一型の複数実装が必要な場合、型だけでは依存を一意に決定できず、手動設定が残る。「ほとんどの設定が省略できる」という主張の適用範囲は、こうした例外の頻度が示されていないため不明である
- **インダイレクション自体が複雑さの源泉になる**: 抽象層が増え、依存グラフが深くなれば、どこで何が起きているかの追跡は容易ではなくなる。複雑さが掛け算で効かなくなるという大規模適用時の効果には根拠が不足している
- **単体テストと DI の相関は限定的**: 純粋関数や Value Object は DI と無関係にテストしやすい。逆に DI されていても、内部状態やグローバルな副作用があればテストは困難なままであるため、相関の向きと強さは不明である
- **サービスロケーターの境界が未定義**: 「アプリケーションルートや表層コードに限れば許容」とされるが、「限られたクラス」の範囲が示されておらず、アンチパターンを判定する実務基準として機能しにくい
- **モックの暗黙的な仕様依存**: テストでモックの期待値を設定する時点で、依存先クラスの変換仕様に暗黙的に依存している。「単体テストが隣接クラスの変更で壊れない」という主張は完全ではない

## 議論用の問い

1. サービスロケーターを「表層コードに限れば許容」とするなら、Laravel のファサードや Django のグローバル設定参照のようなフレームワーク標準のサービスロケーター的機構をどこまで例外として認めるか。チームとして線を引くならどこか
2. オートワイヤリングが効かない「同一型の複数実装」ケースは、実務でどの程度ありふれているか。そのとき、手動設定を書く、インターフェースを分ける、DI をあきらめる、という設計判断をどう決めるか
3. 「単体テストはアーキテクチャの設計をテストしている」という主張をどう評価するか。設計が良いのにテストが書きにくいケース、または設計が悪いのにテストが通るケースを、自分たちの経験から挙げられるか

== 理解の視点

**拾った主張**
- DI（依存性注入）とは、オブジェクトが使う機能の実体を自力で解決せず、常に外部から与えてもらう設計方針である
- 依存を内部で自力生成するクラスは、別パッケージの変更影響を直接受け、単体テストも困難になる
- 依存をコンストラクターで外から受け取る形にすると、「使用の責務」と「生成の責務」が分離される
- 生成の責務を担う専用クラス（Factory や DI コンテナ）が、依存するインスタンスを組み立てて渡す
- DI を徹底すると依存が連鎖的につながり、最上位にたったひとつのルートオブジェクトが生まれる
- DI コンテナは、インスタンス生成と重複防止を管理する仕組みを一般化したフレームワークである。自分で Factory を書く代わりに設定ファイルで宣言する
- オートワイヤリングは、型宣言から依存関係を自動決定できる場合に設定の記述を省略できる機能である。残るのは特別なカスタマイズ設定だけになる
- サービスロケーターは、各クラスが能動的にコンテナから依存を取得する方式であり、アンチパターンである。依存が手続きに埋もれ、単体テストも困難になる
- 抽象に対応する具象が1つだけでも、それはパッケージ間の接続点として DIP の目的にかなう意味を持つ
- 単体テストしやすいクラスと DI 可能なクラスには正の相関があり、単体テストはアーキテクチャ設計の確認ツールでもある

**気にした論点**
- 「使用と生成の分離」がなぜ重要かは理解できたが、依存チェーンをたどると最上位にルートオブジェクトひとつになるという一般化の感覚はまだぼんやりしている
- サービスロケーターと DI の違いは「与えられるか、取りに行くか」だと理解したが、「アプリケーションルートや表層コードに限れば許容」という境界線を具体的にどう判断するかは掴みきれない
- 「単体テストした結果がアーキテクチャ設計を検証している」という主張は直感的にはわかるが、もう少し踏み込んだ説明が必要である

**結論**

この章は、オブジェクトの依存を外から与える DI という設計方針により、使用、生成、管理の3つの責務を分離し、単体テストしやすく変更に強いアーキテクチャを得る方法を説明している。

**残した保留**
- DI コンテナのオートワイヤリングが「透明になる」とされる一方で、問題が起きたときにどこを見ればよいかというデバッグの手がかりには触れられていない。実際に使い始めたときに困りそうである
- 多態のバリエーションがなくてもインターフェースに意味があるという主張は論理として受け取れるが、「今ここでインターフェースを切るべきか」という設計判断の基準はまだわからない

== 実務の視点

**拾った主張**
- **使用と生成の責務分離**: クラスは使うことだけを知ればよく、生成はコンストラクター注入で外に追い出す。テスト可能性と変更耐性が同時に上がる。クラスが他クラスを直接 `new` しており、将来の差し替えが見える場合に適用できる
- **コンストラクター注入で依存を可視化**: 依存一覧がコンストラクターに現れるので、結合度の肥大に早く気づける
- **枯れた DI コンテナを最初から選ぶ**: 自作ファクトリはリファクタリングのたびに書き換えが発生し、ロジックが入ると単体テストまで引きずる。個人開発や短期開発以外のプロジェクトでは、最初から DI コンテナを選ぶことでそのコストを抑えられる
- **オートワイヤリングで設定のボイラープレートを排除**: クラス設計を変更してもコンフィグを触らずに済み、複数人で並列開発するときのコンフリクトを減らせる
- **サービスロケーターはアンチパターン**: コンテナを能動的に取りに行く方式は依存を手続きに潜ませ、後から密結合が発覚する。表層コードだけに限定すべきである

**気にした論点**

**後付け DI 化のコスト**
- 既存コードが至るところで `new` を直書きしているプロジェクトへの適用は一筋縄ではいかない。「全面書き換え」と「局所的に始める」の判断基準は本文に出てこない

**フレームワーク依存**
- 説明が Symfony ServiceContainer を前提にしている。Laravel や Spring で同じことを実現する場合の差分は別途調べる必要がある

**オートワイヤリングが効かないパターン**
- 同一クラスのインスタンスを複数作る場合（Fizz ルールと Buzz ルール）は手書き設定が残り続ける。実務でよくある「同じ型の接続先を切り替えたい」ケースの設計判断が示されていない

**フレームワーク内蔵のサービスロケーター的機能との折り合い**
- Laravel のファサードや Django のグローバル設定参照は、本文の定義でいえばアンチパターンに相当する。チームとしてどこまで許容するかのラインを別途決める必要がある

**結論**

コンストラクター注入と DI コンテナは、複数人での開発と長期保守を前提とするプロジェクトで、テスタビリティと変更耐性を同時に確保するための実用的な土台として、最初のアーキテクチャ選択に組み込む価値がある。

**残した保留**
- 既存コードへの後付け DI 化を、どのタイミングと範囲から始めると費用対効果が出るのかが示されていない
- 同一型の複数インスタンスが必要になる実務でありがちなケースで、オートワイヤリングに頼れない部分の設計指針が不明である
- フレームワーク標準のサービスロケーター的機構をどこまで DI 原則の例外として認めるか、チームルールの決め方が示されていない

== 批評の視点

**拾った主張（崩れる条件付き）**
- **「DI を徹底すれば複雑さが掛け算で効く辛さを忘れられる」** → 抽象層やインターフェースが増えるにつれて、インダイレクション自体が複雑さの新たな源泉になる。依存グラフが深くなれば、どこで何が起きているかの追跡は容易ではない
- **「単体テストしやすいクラスと DI 可能なクラスには正の相関がある」** → 純粋関数や Value Object は DI とは無関係にテストしやすい。逆に DI されていても、内部状態やグローバルな副作用があればテスト困難なままであり、相関の向きと強さは不明である
- **「オートワイヤリングにより、開発者はクラスと単体テストだけに集中でき、コンフリクトの心配がなくなる」** → 同一型の複数実装が存在する場合、型だけでは一意に決定できず手動設定が必要になる
- **「単体テストは実挙動ではなくアーキテクチャの設計をテストしている」** → テストが `convert` の呼び出し回数や引数、`write` の呼び出しシーケンスを検証しているだけなら、インタラクションパターンのテストであって、アーキテクチャの検証とは言いにくい
- **「サービスロケーターは多用がアンチパターンで、アプリケーションルートや限られたクラスに限定すれば許容される」** → 「限られたクラス」の境界が未定義のままであり、実務の判断基準として機能しない

**気にした論点**
- Symfony ServiceContainer を選んだ根拠は、PHP 標準パッケージマネージャでインストールできることにほぼ限られている。他の DI コンテナとの比較がなく、具体例を一般的な DI の理解へ転用できるかが不明である
- イミュータブルなオブジェクトは複数インスタンスを生成する意味がないという前提は、マルチスレッド環境や識別性が必要なケースでは成立しない
- 抽象に対して具象がひとつしかなくても意味があるという命題への論拠が、「不安定側に依存するのはまずい」という説明の繰り返しで止まっている
- 「設定ファイルならロジックにバグが入る心配がない」という主張は、設定ミスがバグにならないという意味ではなく、ロジックバグが入らないという限定的な意味だが、文脈上はより広く読める
- テストの `returnValueMap` の設定が誤っていると `write` の検証も崩れる。モックの期待値も、依存先の変換仕様に暗黙的に依存している

**結論**

使用の責務と生成の責務を分離する中核原則と、それがテスト容易性・変更容易性に寄与する仕組みは、FizzBuzz のコード変遷を通して一定の論理的支持を得ている。一方で、「複雑さが掛け算で効かなくなる」「設計だけに集中できる」という大規模適用時の効果には根拠が不足している。

**残した保留**
- オートワイヤリングが機能しない条件（同一型の複数実装、循環依存、遅延初期化、ランタイム依存解決）がどの程度の頻度で発生するかが示されていない。「ほとんどの設定が省略できる」という主張の適用範囲が不明である
- 「単体テストはアーキテクチャの設計をテストしている」という命題は、章全体のコード例だけでは支えきれない哲学的主張であり、反証が見つかれば覆る
- サービスロケーターの「限定使用なら許容」という例外条件の境界が未定義のままで、アンチパターン判定の実務基準を無効化する可能性がある
