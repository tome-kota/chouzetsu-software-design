# 第8章 デザインパターン（後半）：責務と振る舞い

[前半「多態性とオブジェクト生成」](/chapter-8-1) では、反復、多態性、オブジェクト生成を通じて、パターンを共有語彙として扱う土台を整理した。後半では、その語彙を責務の配置と振る舞いの差し替えに広げる。Facade、Mediator、Proxy、Decorator、Adapter、Compositeで構造を整理し、Strategy、State、Command、Observer、Visitorで振る舞いを扱う。

## 章の主張

デザインパターンとは設計のコードスニペットではなく、「何をすべきでないか」を示す責務の制約として機能する語彙である。構造ではなく目的でパターンを区別することで、オブジェクト間の関係を整理し、責務を明確にする。

## 前提

- Facadeは「利用者が誰一人裏口から直接アクセスしていない」ことが必要条件。その強制手段（言語機能・アーキテクチャテスト・レビュー）は別途用意する必要がある。
- Proxyが機能するには、依存がインターフェース経由になっていることが前提。
- Mediatorの「既存クラスに変更なし」は、各オブジェクトが依存するMediatorのインターフェースが安定していることを前提とする。
- Adapterは「インフラ層での利用に限る」「業務知識を持ち込まない」という制約が守られることを前提とする。
- パターン名で目的を共有するには、チームが「目的の文脈」を同じく読めていることが前提であり、構造が同一のパターン（Proxy/Decorator/Adapter）ではその文脈共有が必須条件になる。

## 実務上の効きどころ

- **Proxy + DI**：既存コードに一切手を入れずにロギング・キャッシュ等の横断的関心事を差し込む。依存がインターフェース経由ならすぐに適用可能。
- **Adapter**：インフラ層の境界でギャップ変換に徹することで、アダプターより手前のロジックを単体テストで検証できる状態を保つ。
- **Command**：UIとユースケースを疎結合にしつつ、コマンドをキューイングして非同期処理に回す設計の余地を作る。CQSのCommandと同義として使える。
- **コードレビューの語彙**：「SingletonにStateを設けるな」「FacadeやMediatorに独自知識を実装するな」という責務の制約として、パターン名を指摘の根拠に使える。

## 弱点と例外

- **Proxy・Decorator・Adapterは構造が同一**であり、目的でしか区別できない。「パターン名で正確なコミュニケーションが成立する」という章の冒頭主張が、この節では文脈依存の解釈に委ねられる形になっており、語彙としての精度が揺らぐ。
- **Mediatorはハブが肥大化するリスク**を抱える。要素が増えるほどMediatorだけが全体の意図を知る状態になり、最初からMediator前提で設計すると構造の見通しが悪くなりうる。
- **Observerはデバッグコストが上がる**。主クラスとオブザーバーが互いを知らない疎結合は保守性として良いが、イベントチェーンが複数になると原因特定が困難になる。
- **Visitorはprotectedアクセス不可**のため、必要な情報をすべてpublicに出す圧力が生まれ、カプセル化を削る方向に設計が動きやすい。
- **Compositeはノード移動が発生するユースケース**では追加の更新処理設計が別途必要になる。ツリーが静的な設定に限っては素直に使える。
- **Facadeの「いくらでもリファクタリングできる」**は、裏口アクセスを排除する強制手段が別に用意されていない限り主張が成立しない。

## 議論用の問い

1. Proxy・Decorator・Adapterは構造が同じで目的でしか区別できないとすると、同一コードを見て複数の開発者が同じパターン名を付けるか。「パターン名が共通語彙になる」という主張はこの条件下でどの程度成立するか。

2. Mediatorの適用タイミングをどこに置くか。「要素が3つ以上で循環依存が出たとき」という目安は、早すぎる過設計と遅すぎる技術的負債の間でどう判断するか。

3. Facadeの「裏口アクセスなし」を実際の現場でどうやって保証するか。言語機能・アーキテクチャテスト・レビュー文化のどれが現実的な担保手段として機能するか。

== 理解の視点

**拾った主張**
**構造を整理するパターン**
- **Facade**：複数の機能オブジェクト群へのアクセスを集約するエージェントオブジェクト。利用者はFacadeのインターフェースだけを知ればよく、中身をいくらリファクタリングしても利用側は影響を受けない。Facadeは抽象レベルの境界線でもある。
- **Mediator**：複数オブジェクトの連携をひとつの仲介オブジェクトに集中させる。各要素は互いを直接知らず、Mediatorだけが全体のコラボレーションを管理する。要素が増えても既存クラスへの変更が最小限で済む。
- **Proxy・Decorator・Adapter**：いずれも呼び出し元と呼び出し先の間に割り込む「ラッパー」だが、目的で区別する。Proxyは元の型に見せかけて振る舞いを拡張する。Decoratorは既存メソッドはそのままに新たなメソッドを追加する。Adapterはインターフェースの型変換を担う（インフラ層の最下層に位置し、ギャップ変換以外の責務を持ってはいけない）。
- **Composite**：自己再帰的なツリー型データ構造の呼び名。要素の親はひとつ（UML用語でコンポジション）。DIコンテナの集約（親が複数ありうる）とは異なる。

**実装形態の補足**
- **クラスか高階関数か**：「振る舞いの詳細を隠蔽した抽象」であれば、クラスでも関数オブジェクト（クロージャ）でもオブジェクト指向の構成要素といえる。デザインパターンはクラスの書き方ではなく設計のパターン。

**振る舞いを外部化するパターン**
- **Strategy**：主クラスはひとつ固定し、外部から振る舞いオブジェクトを注入してバリエーションを得る。実行時に差し替え可能（動的）。Template Methodは継承による静的なバリエーション。
- **State**：オブジェクト自身の状態変化によって自律的に振る舞いが切り替わる。状態を整数・文字列でなく振る舞いオブジェクトで表現する。
- **Command**：UIとユースケースのような「異なる関心を持つ複数の関係者」を疎結合にする。`invoke()` ひとつだけを持つコマンドを介して連携。コマンドをキューイングして実行を遅らせる応用も可能。
- **Observer**：自己完結した主オブジェクトに、外部から追加的な拡張を可能にする。主オブジェクトとオブザーバーの直接依存はなく、ObservableInterfaceだけに依存する。
- **Visitor**：Compositeのような複雑な内部構造に対して、カプセル化を壊さずに未知の操作を追加できる。振る舞いオブジェクトは保持されず使い捨てられる点が他のパターンと異なる。

**パターンを使うときの判断**
- **パターンの正しい使い方**：パターンは外から持ち込むコードスニペットではなく、既存構造から発見するもの。「何をすべきでないか」を示す制約として機能し、責務を明確にして再利用性を高める。

**気にした論点**
- Proxy・Decorator・Adapterは「クラス図が同じ形」と言われると、実際のコードを見たときに三つを即座に区別できる自信がなくなった。
- Mediatorが必要になる「循環依存が自然発生する状況」が、FizzBuzzの例だけだと少し感覚がつかみにくかった。
- CommandとStrategyの「字面が似ているが目的が違う」という説明はわかったが、設計判断の場でどちらを選ぶかがまだ曖昧。
- 「集約（aggregation）」と「コンポジション（composition）」というUML用語が一度だけ出てきたが、説明が短く、Compositeパターンとの関係を整理しきれなかった。

**結論**
複数オブジェクトにまたがる構造パターン（Facade・Mediator・Proxy・Decorator・Adapter・Composite）と、振る舞いを外部化する小さなオブジェクトを使うパターン（Strategy・State・Command・Observer・Visitor）を、「何のための構造か・誰が生成し管理するか」という目的の違いで区別するための語彙の章。

**残した保留**
- Proxy・Decorator・Adapterが実際のコードに現れたとき、三つを正しく区別できるか自信がない（クラス図が同じ形と言われているので特に）。
- Visitorの「使い捨てられる振る舞いオブジェクト」という特徴が、他のパターンとの違いとしてまだ明確に腑に落ちていない。
- StrategyとCommandは「外部から振る舞いを注入する」点が似ているが、実設計でどちらを選ぶかの判断基準が自分の中でまだ固まっていない。

== 実務の視点

**拾った主張**

- **Facade：裏口を塞ぐことが本体**。「利用者が誰一人裏口から直接アクセスしていないこと」が前提条件。インターフェースだけに依存させ、中身を自由にリファクタリングできる状態を保つ。適用条件：パッケージ境界が明確に引けていること。
- **Proxy：DIコンフィグで挿入できる**。`JobWorker`のコードを一切変えずに、DI設定だけでロギングプロクシを差し込める実例が具体的。適用条件：依存がインターフェース経由になっていること。これはすぐ使える。
- **Adapter：薄くしか書いてはいけない、理由がはっきりしている**。「アダプターより手前のロジックを単体テストで検証し、アダプター自体はギャップ変換のみ」という原則。業務知識をアダプターに持ち込まない理由が、テスト困難性から説明されている。
- **Command：キューイングとCQSへの接続**。UIとユースケースの疎結合に加えて、コマンドオブジェクトをストックして非同期処理に回す応用例が明示されている。CQSのCommandもこれと同じと言い切っている点が現場で使える根拠になる。
- **パターン名が「やってはいけないこと」の表明になる**。「SingletonにStateを設けるな」「FacadeやMediatorに独自知識を実装するな」という責務の制約として使う視点。コードレビューでの指摘に語彙として使える。
- **クラスか関数かはパターンの本質ではない**。言語が高階関数をサポートするなら、振る舞いパターン（Strategy、Command等）をクロージャで書いても設計の意味は変わらない。

**気にした論点**
- Mediator：ハブが神クラスになるリスク。複雑さをMediatorに集中させるのは、Mediatorだけが全体の意図を知るブラックボックスになりうる。
- Observer：デバッグ時のイベント追跡コスト。イベントチェーンが複数になると原因特定に時間がかかる。
- Visitor：`protected`アクセス不可の制約が、「とりあえずgetterを生やす」対応を誘発しやすい。
- Composite：ノード移動が発生するユースケースでは更新処理の設計が別途必要。ツリーが静的な設定ならすんなり使える。

**結論**
ロギング・キャッシュ・外部ライブラリ接続などの横断的関心事を既存コードに手を入れずに差し込む設計（Proxy/Adapter）と、UIとユースケースを切り離して非同期化の余地を作る設計（Command）は、自分の仕事で今週から使える。

**残した保留**
- Mediatorの適用タイミングの判断基準：早すぎると過設計、遅すぎると技術的負債になる。現場での閾値が不明。
- Observerのイベント追跡をどう担保するか：大規模になった場合の運用設計が別途必要かどうか未確認。
- Adapterの「薄さ」の判定基準：nullチェック・デフォルト値補完のような少量の条件分岐がアダプターに許容されるかの線引きが不明確。

== 批評の視点

**拾った主張（批評）**
- **「ファサードのインターフェースさえ維持していれば、中身をいくらでもリファクタリングできます」**：裏口アクセスを排除する強制手段が述べられていない。条件が満たされない現場では主張が成立しない。
- **「ソフトウェアの設計とはまさに、多層になった抽象レベルをFacadeパターンで実現するもの」**：「まさに」という断定語で設計全体をFacadeに帰着させており、Facadeが直接関与しない設計判断が除外されている。
- **「メディエーター以外の既存クラスとインターフェースには、何ひとつ無駄な変更が発生しません」**：MediatorのインターフェースそのものがISPの観点から変化しうる。「インターフェースが安定している」という追加前提が必要だが明示されていない。
- **「Proxy・Decorator・Adapterは目的で区別するのがポイント」**：構造が同一で目的だけが異なるなら、命名はチームの解釈に依存する。「パターン名が正確なコミュニケーションを保証する」という冒頭の主張と矛盾する可能性がある。
- **「DataStoreクラスの基本機能はsave()とload()で完結しています」**：save()/load()内部にすでにnotify()呼び出しが組み込まれており、DataStoreはObserverの存在を最初から想定して設計されている。「完結している」は正確ではない。

**気にした論点**
- 「パターンは共通語彙として機能する」（冒頭）と「構造が同じパターンは目的で区別する」（Proxy/Decorator/Adapter節）は、「目的は文脈依存の解釈に委ねられる」という結論を招き、共通語彙としての正確性が揺らぐ。
- Visitorの「言語によっては深刻でない」という記述と「GoFの問題提起には普遍性がある」という主張が同節内で揺れている。

**結論**
Facadeから始まる各パターンの「目的による区別」という枠組みは、構造の類似性に対する正直な認識の上に立っており論理的整合性は保たれている。ただし「語彙が正確なコミュニケーションを実現する」という冒頭の主張は、目的が文脈依存でしか区別できないパターンが存在する以上、そのまま成立しているとは言いきれない。

**残した保留**
- Facadeによる「裏口なし」の保証が言語機能・ツール・チーム規律のどれで担保されるのかの確認が必要。
- Observerの「主クラスは完結している」という記述はnotify()を主クラスが自ら呼ぶ設計と矛盾しないかの整合性確認が必要。
- 「パターン名で目的の共有が成立する」ことの実証的裏付けが示されていない。
- VisitorのGoFパターンとしての普遍性と言語特性によって問題が解消される場合の位置づけが未整理。
