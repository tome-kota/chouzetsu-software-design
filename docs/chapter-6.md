# 第6章 テスト駆動開発

この章の中核は、テストファーストのサイクル（失敗、最小実装、成功、繰り返し）を回すことで、動作保証と抽象・具象の分離設計を同時に得るという考え方にある。BDD が振る舞いの確認に重心を置くのに対し、TDD は変更に強い設計を導く技法として位置づけられる。

## 章の主張

テストファーストのサイクルを回すことで、実装前にインターフェースの仮説を検証し、動作保証と設計の改善を同時に進められる。テスト済みの振る舞いは動く仕様ドキュメントになり、リファクタリングでは動作を変えていないことの確認に使える。TDD は単なるテスト技法ではなく、抽象と具象を分離し、変更に強い設計へ収斂させるための開発技法である。

## 前提

- 依存性注入（DI）が設計に組み込まれており、依存をモック化できる構造になっていること
- 下位モジュールのテストが責務範囲を過不足なくカバーしていること。ただし、これは自己申告であり、章自体がその限界を認めている
- モックの境界を判断できる意味のある粒度で、パッケージ分割が行われていること
- 回帰テストを自動実行できる環境が整っていること

## 実務上の効きどころ

- 新規モジュール設計時にインターフェースの仮説をモックで検証し、実装前に設計ミスを発見できる
- テストコードが「動く仕様ドキュメント」になり、レビューや引き継ぎで文脈を説明するコストが下がる
- リファクタリング時に、動作が変わっていないことをテストで確認できる
- テストしにくさを、単一責任原則（SRP）違反などを疑う設計見直しのシグナルとして使える

## 弱点と例外

- テストケース自体に穴があれば、「下位がテスト済みなら目の前のコードにバグがある」という前提は崩れる。品質保証が自己申告であるという矛盾は解消されていない
- TDD のサイクルを回しても、SRP を満たさない設計のまま開発を続けられる。設計判断は開発者に委ねられたままである
- フレームワーク依存、レガシー統合、グローバル状態など、オブジェクト指向の原則に従っていてもテストしにくい領域があるため、「テストしにくいこと＝原則逸脱」とは限らない
- `PassThroughRule` の `$carry == ""` 判定は暗黙的な実行順序に依存している。章が正しい設計案として提示しながら、この脆弱性に触れていない
- 「シンプルさが拡張性をもたらす」という主張は、「シンプル」の定義が不明確なままで反証しにくい

## 議論用の問い

1. BDD と TDD の使い分けは「適材適所」と言われるが、具体的に何を判断基準に切り替えるべきか
2. テストがなく密結合な既存コードベースに対して、TDD をどの粒度、どの起点から適用し始めるべきか
3. TDD がアーキテクチャを「導き出す」という因果主張は、FizzBuzz という意図的に単純化された問題での成功例に基づいている。複雑なドメインロジックや外部制約の多い実務へ一般化できるか

== 理解の視点

**拾った主張**
- 単体テスト（Unit Test）は、最小単位のモジュールやクラスにフォーカスしたテスト技法である。「テスト」の技法であり、「開発」の技法ではない
- バグの原因は再帰的に下位構造へ広がるため、各層を単体テストで保証しておくと調査範囲を絞り込める
- xUnit（PHPUnit など）は、テストコードをプログラムとして書き、自動実行する仕組みである。`assertEquals` などのアサーションメソッドで期待値と実結果を比較する
- 境界値テストでは、エッジケースのテストが通れば、無難な値のテストを大量に用意する必要はない
- テストを下位モジュールから積み上げると、上位で不具合が出たときに調査対象のスコープを絞れる
- 回帰テスト（リグレッションテスト）は、変更のたびに既存テストをすべて再実行すること。自動化されているため継続できる
- スタブは依存クラスの代わりに決まった値を返す疑似オブジェクトであり、「仮に期待どおりの答えを得たとしたら」と仮定するために使う
- モックは呼び出しの有無やパラメーターの正しさを検証する疑似オブジェクトであり、単体テストのアサーションとして意味を持つ
- コンストラクター注入（DI）でオブジェクトを外から渡すとモック化しやすくなる。`new` で依存を自力生成するとテストしにくい
- テストのために `private` を `public` にするなど、設計を歪める変更は禁止する。テストしにくさはクラス設計を見直すためのバロメーターになる
- テストファーストでは、実装より先にテストを書く。失敗を確認してから最小実装を書くことが鉄則である
- TDD の基本サイクルは、①テスト追加、②失敗確認、③最小限の実装、④成功、を繰り返すこと。テスト済みの振る舞いが「動く仕様ドキュメント」になる
- リファクタリングは、動きを変えずにコードを整理すること。テストが通ることが「動作が変わっていない」保証になる
- BDD（振る舞い駆動開発）は、ユーザー機能レベルでテストファーストを行い、「仕様どおりに動く実装を得る」ことを目的にする
- BDD と TDD の違いは、BDD が振る舞いの結果を問うのに対し、TDD は内部設計の整合性、特に抽象と具象の分離を重視する点にある
- DRY 原則は、同じ意味のことを繰り返さないという考え方である。複数箇所を同期して変更しなければならない設計は壊れやすく、技術的負債になる
- インターフェース設計の仮説、テスト、実装、気づき、仮説の見直しというサイクルで、設計は収斂していく。最初の仮説が間違っていることは前提にしてよい
- TDD を活用すると SRP を満たすクラス設計を目指しやすくなる。クラスとテストケースが原則として1対1に対応することは、設計の指針になる

**気にした論点**
- スタブとモックの使い分けは、「スタブは仮定、モックは検証」と整理できる。一方で、「パッケージ内は直接依存でよく、パッケージをまたぐときだけモック化する」という判断基準を実務でどう適用するかは曖昧である
- `ReplaceRuleInterface` の第1案から第2案への改訂で、`replace(n)` から `apply(carry, n)` と `match(carry, n)` に分割する必然性の流れが追いにくい
- TDD の第1段階と第2段階の切り替え、つまり「BDD 的な振る舞いを作る段階」から「設計のための TDD」へ移るタイミングが具体的ではない

**結論**

この章は、テストファーストのサイクルを通じて動作保証と設計、つまり抽象と具象の分離を同時に得るための TDD を説明している。

**残した保留**
- BDD と TDD の使い分けの判断がまだ明確ではない。「適材適所」と言われても、どの条件で切り替えるかがわからない
- `createMockRule` のパラメーターが増えて複雑になったコードを「やることはシンプル」と言い切っているが、ゼロから同じ設計を書けるかは自信がない
- 「テストを書きにくいと感じたら SRP 違反などのバロメーター」という主張は理解できるが、どの程度をもって「書きにくい」と判断するかの感覚が残っている

== 実務の視点

**拾った主張**
- 単体テストは下から積み上げる。各下位モジュールのテストが責務範囲を過不足なくカバーしていれば、上位で不具合が出たときに調査スコープを目の前のコードへ絞れる
- 境界値に絞ってテストする。判定分岐や飽和処理など、端で壊れやすいロジックがある場合、無難な値を大量に試すより効率的である
- スタブとモックで依存を分離する。DI が設計に入っていれば、まだ実装されていない下位モジュールがあっても上位のテストを書ける
- テストしにくい設計は、オブジェクト指向の原則違反を疑うバロメーターになる。`private` を `public` に変えてテストを通そうとする衝動は、設計を再レビューするサインである
- TDD は振る舞いではなく設計の整合性を問う技法であり、変更に強いアーキテクチャを目的とするときに BDD と区別して使える
- モック化はパッケージ境界で行う。ただし、前提としてパッケージ分割が意味のある粒度で行われていなければならない

**気にした論点**

**使える場面**
- 新規機能を設計段階から作るとき。TDD のサイクルでインターフェースの設計ミスを実装前に発見できる

**使いにくい場面**
- 既存コードベースにテストが一切ない状態から始めるときや、「とりあえず動くもの」を優先する短納期フェーズ

**導入コスト**
- 手順自体はシンプルだが、「失敗を確認してから成功させる」順序を守る習慣がチームに定着するまで時間がかかる

**既存手法との差分**
- 最初は遅く感じても後半で差が出る構造だが、短命なコードには投資が割に合わない場合がある

**結論**

新規モジュールの設計時にテストファーストのサイクルを使い、インターフェースの仮説をモックで検証する習慣を自分の担当領域に取り込む。

**残した保留**
- テストがなく密結合な既存コードに対して、どこから、どの粒度でテストを足し始めるかの判断基準が本文では示されていない
- TDD 未経験者が「最小限の実装を意図的に書く」作法を体得するまでのコストが読めない
- CI/CD が整備されていない環境での運用コストには触れられていない
- モック過多によってテストが硬直する問題がある。インターフェースが変わるたびに、モックのパラメーターを大量に修正する実態が本文後半から見える

== 批評の視点

**拾った主張（崩れる条件付き）**
- 「下位モジュールがすべて単体テスト済みなら、バグの原因は目の前の自分のコードにある」 → テストケース自体に穴があれば成立しない。本文も品質保証が自己申告であると認めているため、この断定は自己参照的に弱い
- 「テストしにくいコードはオブジェクト指向原則を逸脱しているバロメーター」 → フレームワーク依存コード、レガシー統合、グローバル状態管理など、原則に従っていても構造的にテストしにくい領域がある
- 「TDD を回せば自然に SRP を目指すことになる」 → TDD は実装の手順を制約するが、設計判断はなお開発者に委ねられる
- 「拡張性に役立つのは高度なメカニズムよりコードのシンプルさ」 → 「シンプル」の定義が不明確なままで、反証しにくい
- 「モックはスタブと違いアサーションとして意味がある」 → モックが仕様と乖離した呼び出しパターンを検証している場合、テストコードのバグを埋め込む可能性がある

**気にした論点**
- 「単体テストの品質保証は自己申告」と認めながら、その後の議論ではテストの積み上げを信頼できる基盤として前提に戻っている。この自己矛盾が解消されていない
- パッケージ境界でモック化する判断基準を支える論拠、つまりなぜパッケージ境界が適切な分離点なのかが具体的に示されていない
- `PassThroughRule` の `$carry == ""` 判定は実行順序に依存しており、ルールの追加順序が変わると壊れる可能性がある。しかし、章ではこの脆弱性に触れず、第2案を正しい仮説として扱っている
- TDD を実践した開発者の方が、実践しない開発者より設計品質が向上したという主張を裏付ける実証データが存在しない

**結論**

単体テストの積み上げと回帰テストの自動化によって変更コストを下げるという主張は、論理的に支えられており、この章の中で最も堅固な部分である。

**残した保留**
- 「テストしにくいこと＝オブジェクト指向原則の逸脱」は、因果の方向が逆である可能性がある
- `PassThroughRule` の `$carry == ""` 判定が実行順序に依存していることは、第2案を正しい仮説として扱う章の論拠を部分的に崩す可能性がある
- TDD がアーキテクチャを「導き出す」という因果主張は、FizzBuzz という意図的に単純化された問題での成功例に基づいており、複雑なドメインロジックへ一般化できるかは保留である
